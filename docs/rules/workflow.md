# Git 및 PR 작업 규칙

## 기본 원칙

- `main`은 배포 가능한 기준 브랜치로 유지한다.
- 한 브랜치와 한 PR은 하나의 목적만 가진다.
- 다른 작업자의 변경과 커밋되지 않은 파일을 덮어쓰지 않는다.
- 범위 밖 변경은 발견하더라도 같은 PR에서 정리하지 않는다.
- commit, push, PR 생성, Ready 전환, 병합, 브랜치 삭제와 배포는 각각
  별도의 상태 변경이다.
- 사용자가 명시적으로 요청한 단계까지만 수행한다.

commit 요청은 push 권한이 아니며, push 요청은 PR 생성이나 병합 권한이
아니다. 강제 push, 공유 브랜치 삭제, PR 병합과 배포는 항상 명시적
승인을 받는다.

## 작업 시작

### 작업 트리 확인

작업 전에 다음을 확인한다.

```bash
git status --short --branch
git branch --show-current
git log -5 --oneline
```

- dirty worktree의 기존 변경은 사용자 소유로 취급한다.
- 요청과 무관한 변경을 restore, stash, amend 또는 commit하지 않는다.
- 기존 변경과 같은 파일을 수정해야 하면 원래 diff를 읽고 보존한다.
- 여러 목적의 작업이 섞일 위험이 있으면 격리된 worktree를 사용한다.

### 브랜치 이름

```text
<type>/<short-topic>
```

허용 type:

- `feat`: 사용자 기능
- `fix`: 오류 수정
- `refactor`: 동작 변화 없는 구조 변경
- `perf`: 성능 개선
- `docs`: 문서 변경
- `chore`: 유지보수
- `build`: 빌드와 배포 구성

예:

```text
feat/ocr-camera
refactor/fsd-structure
docs/project-rules
```

## 커밋

### 제목 형식

```text
<type>(<scope>): <명사형 제목>
```

- scope는 선택 사항이다.
- 콜론 뒤에 공백을 하나 둔다.
- 한글 제목을 사용하고 50자 이내로 작성한다.
- 제목만 읽어도 변경된 대상과 결과를 구분할 수 있어야 한다.
- `추가하라`, `수정하라`, `구현하라` 같은 명령형·동사형을 사용하지
  않는다.
- `문서 추가`, `오류 수정`, `화면 구현`, `구조 정리`처럼 변경 결과를
  나타내는 명사형으로 끝낸다.

올바른 예:

```text
docs(ocr): OCR 처리 방식 비교 문서 추가
feat(scan): 영양성분 촬영 화면 구현
fix(router): 상세 화면 이동 오류 수정
refactor(theme): 테마 토큰 구조 통합
```

잘못된 예:

```text
docs(ocr): 처리 방식 비교 문서를 추가하라
feat(scan): 촬영 화면을 구현하라
fix: 수정
update files
```

### 본문

- 제목 다음에 빈 줄을 둔다.
- 오타나 포맷처럼 자명한 변경을 제외하면 본문을 작성한다.
- 파일 목록보다 변경 이유와 선택한 방향을 설명한다.
- 고려했지만 선택하지 않은 중요한 대안이 있으면 기록한다.
- 사용자에게 보이는 동작 변화가 있으면 명시한다.
- 검증하지 못한 항목과 알려진 제한사항을 숨기지 않는다.
- 72자 안팎에서 줄바꿈한다.

예:

```text
docs(structure): FSD 프로젝트 구조 설계 추가

Expo Router와 기능 코드의 책임을 분리하기 위해 FSD 레이어와
의존 방향을 정의한다.

사용자에게 보이는 동작 변화는 없다.
```

관련 이슈는 `Refs: #12`, 호환성을 깨는 변경은
`BREAKING CHANGE:` 푸터로 기록한다.

### 커밋 단위

- 한 커밋에는 하나의 목적만 포함한다.
- 독립적으로 검토하거나 되돌릴 수 있는 변경을 분리한다.
- 리팩터링과 사용자 동작 변경을 가능한 한 분리한다.
- 생성 파일이나 lockfile은 원인이 되는 변경과 같은 커밋에 포함한다.
- 커밋 전에 스테이징된 파일과 diff를 확인한다.

```bash
git diff --cached --stat
git diff --cached --check
```

## push와 원격 작업

- push 전에 현재 브랜치, upstream과 전송할 커밋을 확인한다.
- 사용자가 push를 요청하지 않았다면 로컬 커밋까지만 수행한다.
- `main` 직접 push는 저장소 정책과 사용자 지시를 모두 확인한다.
- 강제 push는 공유 이력을 바꾸므로 명시적 승인 없이 실행하지 않는다.
- push 뒤에는 로컬 HEAD와 원격 추적 브랜치가 같은지 확인한다.

## PR 흐름

### Draft PR과 작업 이력

PR 번호가 필요한 작업 이력을 같은 PR에 포함하기 위해 다음 순서를
사용한다.

1. 첫 번째 의미 있는 커밋을 push한다.
2. Draft PR을 생성해 PR 번호를 확보한다.
3. 구현과 필수 검증을 완료한다.
4. `docs/history/YYYY-MM-DD-pr-<number>-<topic>.md`를 작성한다.
5. 이력 문서를 같은 PR 브랜치에 커밋하고 push한다.
6. 검토 준비 상태를 확인한 뒤 Ready for review 전환 승인을 받는다.

push나 PR 생성이 요청되지 않은 로컬 구현에서는 PR 번호를 추측하지
않는다. [`docs/history/_template.md`](../history/_template.md)만 유지하고
외부 작업 요청을 기다린다.

### PR 제목

- 커밋과 같은 명사형 제목 규칙을 사용한다.
- 여러 커밋을 포괄하는 실제 결과를 제목에 쓴다.
- 구현 과정이나 내부 작업 순서를 제목에 나열하지 않는다.

### PR 본문

다음 내용을 포함한다.

- 작업 배경과 목표
- 주요 변경
- 핵심 기술 결정
- 사용자에게 보이는 변화
- 실제 검증 명령과 결과
- 스크린샷 또는 영상이 필요한 UI 변화
- 제외 범위와 후속 작업
- 관련 이슈와 설계·계획·이력 문서

실패한 검증이나 실행하지 못한 검증을 통과로 표현하지 않는다.

## 리뷰

- 리뷰 의견을 그대로 적용하기 전에 현재 코드와 공식 문서로 확인한다.
- 불명확하거나 기술적으로 의심되는 의견은 재현과 근거를 먼저 찾는다.
- 수정은 같은 PR 브랜치에 목적별 커밋으로 추가한다.
- 리뷰 범위를 넘어서는 제안은 후속 작업으로 분리한다.
- 리뷰 요청 전에 필수 검증과 PR 이력 문서를 확인한다.

## 병합과 정리

- 필수 검증이 실패한 상태에서는 병합하지 않는다.
- merge, squash, rebase 중 사용할 방식은 저장소 설정과 사용자 지시를
  따른다.
- 병합 방식이 확정되기 전에는 임의로 커밋 이력을 재작성하지 않는다.
- 병합과 원격 브랜치 삭제는 별도 요청을 받은 뒤 수행한다.
- 병합 뒤 PR 이력 링크와 상태가 실제 결과를 반영하는지 확인한다.

## 금지 사항

- 요청 없이 `main`에 직접 commit 또는 push
- 다른 작업자의 변경을 `git restore`, reset 또는 checkout으로 제거
- 명시적 승인 없는 강제 push와 공유 브랜치 삭제
- 실패한 검증을 숨기거나 성공으로 기록
- 하나의 PR에 무관한 리팩터링과 기능 변경 혼합
- PR 번호, 검증 결과 또는 배포 결과 추측
