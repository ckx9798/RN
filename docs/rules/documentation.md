# 문서 관리 규칙

## 목적

프로젝트 문서가 서로 다른 사실을 기준으로 삼지 않도록 문서별 책임,
저장 위치와 갱신 시점을 정의한다.

## 문서 종류와 위치

| 문서 | 위치 | 책임 |
| --- | --- | --- |
| 프로젝트 소개 | `README.md` | 지원 플랫폼, 설치, 실행과 규칙 문서 진입점 |
| 에이전트 지침 | `AGENTS.md` | 작업 전에 필요한 핵심 제약과 상세 규칙 링크 |
| 기여 안내 | `CONTRIBUTING.md` | 브랜치부터 리뷰까지의 실행 순서 |
| 상세 규칙 | `docs/rules/` | 주제별 단일 기준 |
| 설계 | `docs/superpowers/specs/` | 구현 전 승인된 요구사항과 결정 |
| 구현 계획 | `docs/superpowers/plans/` | 승인된 설계의 작업·검증·커밋 순서 |
| PR 작업 이력 | `docs/history/` | PR별 실제 변경, 결정과 검증 결과 |
| 조사 자료 | `docs/` | 기술 선택 전에 비교한 근거 자료 |

Superpowers 설계와 계획 문서는 기본 경로에서 이동하지 않는다. 구현이
완료돼도 원래 경로를 유지하고, PR 결과는 별도의 이력 문서로 정리한다.

## 문서 상태

설계와 계획처럼 검토가 필요한 문서는 머리말에 다음 상태 중 하나를
기록한다.

- `초안`: 작성 중이며 구현 기준으로 사용할 수 없음
- `검토 요청`: 내용이 완성돼 승인을 기다리는 상태
- `승인`: 구현 기준으로 사용할 수 있는 상태
- `대체`: 더 새로운 기준 문서로 교체된 상태
- `폐기`: 구현하지 않기로 결정한 상태

`대체`나 `폐기` 상태에는 이유와 후속 기준 문서 링크를 함께 남긴다.

## 파일명

- 설계: `YYYY-MM-DD-<topic>-design.md`
- 구현 계획: `YYYY-MM-DD-<topic>.md`
- PR 이력: `YYYY-MM-DD-pr-<number>-<topic>.md`
- 상세 규칙: 날짜 없이 책임을 나타내는 이름을 사용한다.
- 파일명은 영문 kebab-case를 사용한다.

## PR별 작업 이력

### 생성 시점

1. 첫 번째 의미 있는 커밋을 push한다.
2. Draft PR을 생성해 PR 번호를 확보한다.
3. 구현과 필수 검증을 마친다.
4. `docs/history/YYYY-MM-DD-pr-<number>-<topic>.md`를 작성한다.
5. 이력 문서를 같은 PR 브랜치에 커밋한다.
6. 검토 준비가 끝난 뒤 Ready for review 전환 여부를 확인한다.

push나 PR 생성이 요청되지 않은 로컬 작업에서는 PR 이력 파일을
추측해서 만들지 않는다. 대신 [`docs/history/_template.md`](../history/_template.md)
형식만 유지하고 외부 작업 승인을 기다린다.

### 필수 내용

- 날짜, PR 번호와 링크, 상태
- 관련 설계와 구현 계획
- 작업 배경과 목표
- 작업 범위와 주요 변경
- 핵심 기술 결정과 선택 이유
- 사용자에게 보이는 변화
- 실제로 실행한 검증 명령과 결과
- 제외 범위와 후속 작업

PR 이력은 변경 파일 목록만 나열하지 않는다. 설계와 계획의 내용을
복사하지 않고 실제 구현이 결정과 달라진 부분을 분명히 기록한다.

### 생략할 수 있는 경우

이력 문서 자체의 오타, 깨진 링크 또는 메타데이터만 고치는 문서 전용
PR은 새로운 이력 문서를 만들지 않아도 된다. 기능, 오류 수정, 구조,
의존성, 설정과 실질적인 규칙 변경은 이력 문서를 남긴다.

## 갱신 책임

- 코드가 규칙이나 설계의 설명과 달라지면 같은 PR에서 문서를 갱신한다.
- 기준이 바뀌면 기준 문서를 먼저 수정하고 요약 문서의 링크와 표현을
  함께 확인한다.
- 문서 링크를 이동할 때는 저장소 전체 참조를 검색해 함께 수정한다.
- 실행하지 않은 검증을 통과했다고 기록하지 않는다.
- 현재 상태와 목표 상태를 한 문단에서 섞지 않는다.

## 중복과 충돌

- 상세 규칙은 `docs/rules/`의 해당 주제 문서 한 곳에만 정의한다.
- 루트 문서는 상세 규칙을 요약할 수 있지만 다른 기준을 만들지 않는다.
- 문서가 충돌하면 `AGENTS.md`에 정의된 우선순위를 적용한다.
- 오래된 결정은 조용히 삭제하지 않고 대체 또는 폐기 상태와 이유를
  남긴다.

## 문서 전용 변경 검증

- `git diff --check`로 공백과 충돌 표시를 확인한다.
- 상대 링크가 실제 파일을 가리키는지 확인한다.
- 명령어와 파일 경로가 현재 저장소에 존재하는지 확인한다.
- 미완성 표현과 사실처럼 보이는 예시 검증 결과를 남기지 않는다.
