# 프로젝트 규칙 체계 설계

- 작성일: 2026-09-30
- 상태: 검토 요청
- 대상: 프로젝트 참여자와 AI 에이전트

## 배경

현재 `AGENTS.md`에는 Expo, 플랫폼, 구조, 스타일, 상태 관리, 검증과
커밋 규칙이 함께 들어 있다. 그러나 Git 브랜치와 PR 운영, 문서 보관,
배포, 보안 규칙은 충분히 정의되어 있지 않다. 승인된 FSD 설계와 현재
`AGENTS.md`의 디렉터리 규칙도 서로 충돌한다.

프로젝트가 커져도 규칙을 찾기 쉽고 같은 내용을 여러 파일에서 다르게
설명하지 않도록, 짧은 진입 문서와 주제별 상세 문서로 규칙 체계를
나눈다.

## 목표

- 사람과 AI 에이전트가 동일한 개발·Git·PR 규칙을 사용한다.
- 규칙의 기준 문서와 우선순위를 명확히 한다.
- 프로젝트 구조를 FSD 기준으로 확정한다.
- 설계와 구현 계획은 Superpowers 기본 위치를 사용한다.
- 구현 결과는 PR 단위의 영구 이력 문서로 남긴다.
- 규칙이 실제 명령과 저장소 설정으로 검증 가능하도록 작성한다.

## 문서 체계

### 루트 문서

| 파일 | 역할 |
| --- | --- |
| `README.md` | 프로젝트 소개, 지원 플랫폼, 설치와 실행 방법 |
| `AGENTS.md` | AI 에이전트가 즉시 지켜야 할 핵심 제약과 상세 규칙 링크 |
| `CONTRIBUTING.md` | 사람과 에이전트가 공유하는 Git, 커밋, PR 작업 흐름 |

`AGENTS.md`는 모든 상세 내용을 복사하지 않는다. 작업 전에 반드시 알아야
하는 제약을 직접 기록하고, 설명이 긴 항목은 `docs/rules/`의 기준 문서로
연결한다.

### 상세 규칙

```text
docs/
  README.md
  rules/
    architecture.md
    development.md
    workflow.md
    documentation.md
    release.md
  history/
  superpowers/
    specs/
    plans/
```

- `docs/README.md`: 문서 지도와 문서 종류별 저장 위치
- `docs/rules/architecture.md`: FSD 레이어, 의존 방향, 라우팅, 임포트
- `docs/rules/development.md`: Expo, 플랫폼, 스타일, 상태, 의존성, 검증
- `docs/rules/workflow.md`: 브랜치, 커밋, push, PR, 리뷰와 병합
- `docs/rules/documentation.md`: 문서 작성, 갱신, 상태와 이력 관리
- `docs/rules/release.md`: EAS Build, Submit, Update와 릴리스 승인
- `docs/history/`: PR별 구현 완료 기록
- `docs/superpowers/specs/`: 진행 중이거나 참조할 설계 문서
- `docs/superpowers/plans/`: 승인된 설계의 구현 계획

### 규칙 우선순위

충돌이 생기면 다음 순서로 판단한다.

1. 현재 작업에서 사용자가 명시한 요구사항
2. 저장소 루트의 `AGENTS.md`
3. `CONTRIBUTING.md`와 `docs/rules/`의 기준 문서
4. 승인된 기능 설계와 구현 계획
5. 기존 코드의 관례

상위 규칙과 충돌하는 하위 문서는 임의로 해석하지 않고 사용자에게
확인한다. 동일한 우선순위의 문서가 충돌하면 더 최근에 승인된 결정을
적용하고, 오래된 문서를 함께 수정한다.

## Git 작업 흐름

### 브랜치

- `main`은 배포 가능한 기준 브랜치로 유지한다.
- 기능 작업은 목적별 브랜치에서 수행한다.
- 브랜치 이름은 `<type>/<short-topic>` 형식을 사용한다.
- type은 `feat`, `fix`, `refactor`, `perf`, `docs`, `chore`, `build` 중
  하나를 사용한다.
- 하나의 브랜치는 하나의 PR 목적만 가진다.
- 다른 작업자의 변경과 커밋되지 않은 변경을 덮어쓰지 않는다.

예:

```text
feat/ocr-camera
refactor/fsd-structure
docs/project-rules
```

### 외부 상태 변경 권한

- commit, push, PR 생성, 병합, 배포는 각각 별도의 상태 변경이다.
- 사용자가 요청한 단계까지만 수행한다.
- 커밋 요청이 push나 PR 생성 권한을 포함하지 않는다.
- push 요청이 PR 생성이나 병합 권한을 포함하지 않는다.
- 강제 push, 브랜치 삭제, PR 병합과 배포는 항상 명시적 요청이 필요하다.

## 커밋 규칙

### 제목

```text
<type>(<scope>): <변경 내용을 나타내는 명사형 제목>
```

- type 뒤 scope는 선택 사항이다.
- 콜론 뒤에는 공백을 하나 둔다.
- 제목은 한글로 작성하고 50자 이내로 제한한다.
- `추가하라`, `수정하라`, `구현하라` 같은 명령형·동사형을 사용하지
  않는다.
- `추가`, `수정`, `구현`, `정리`, `제거`, `도입`처럼 변경 결과가
  드러나는 명사형으로 끝낸다.
- 제목만 보고 변경 범위를 구분할 수 있어야 한다.

예:

```text
docs(ocr): OCR 처리 방식 비교 문서 추가
feat(scan): 영양성분 촬영 화면 구현
fix(router): 상세 화면 이동 오류 수정
refactor(theme): 테마 토큰 구조 통합
```

### 본문

- 제목 다음에 빈 줄을 둔다.
- 자명한 오타나 포맷 변경을 제외하면 본문을 작성한다.
- 변경 파일 목록보다 변경 이유와 선택한 방향을 설명한다.
- 사용자에게 보이는 동작 변화가 있으면 명시한다.
- 검증하지 못한 항목과 알려진 제한사항을 숨기지 않는다.
- 본문은 72자 안팎에서 줄바꿈한다.
- 관련 이슈는 `Refs: #12`, 호환성 파괴는 `BREAKING CHANGE:` 푸터로
  기록한다.

### 커밋 단위

- 한 커밋에는 하나의 목적만 포함한다.
- 독립적으로 되돌릴 수 없는 서로 다른 목적을 한 커밋에 섞지 않는다.
- 리팩터링과 사용자 동작 변경은 가능한 한 분리한다.
- PR 이력 문서는 해당 구현과 같은 PR에 포함하되 별도 문서 커밋으로
  분리할 수 있다.

## PR 규칙

### 생성과 상태

- 첫 번째 의미 있는 커밋을 push한 뒤 Draft PR을 생성해 PR 번호를
  확보한다.
- 구현과 검증이 끝나기 전에는 Ready for review로 전환하지 않는다.
- PR은 하나의 목적과 독립적으로 검토 가능한 크기를 유지한다.
- 범위가 커지면 후속 PR로 분리하고 현재 PR의 제외 범위에 기록한다.

### PR 제목과 본문

- PR 제목은 커밋 제목과 같은 명사형 규칙을 사용한다.
- PR 본문에는 배경, 주요 변경, 사용자 영향, 검증 결과, 제외 범위,
  후속 작업, 관련 이슈를 포함한다.
- UI 변경은 가능한 경우 iOS와 Android 스크린샷 또는 영상을 첨부한다.
- 실패한 검증이나 실행하지 못한 검증을 성공으로 표현하지 않는다.

### 리뷰와 병합

- 리뷰 의견은 재현하거나 근거를 확인한 뒤 반영한다.
- 리뷰 수정은 기존 PR 브랜치에 추가한다.
- 필수 검증이 실패한 상태에서는 병합하지 않는다.
- 병합 방식과 브랜치 삭제는 저장소 설정이 확정될 때 별도 규칙으로
  보완한다. 그 전에는 사용자의 명시적 지시를 따른다.

## PR별 작업 이력

### 목적

`docs/history/` 문서는 PR이 병합된 뒤에도 작업 배경과 구현 결과를
이해하기 위한 영구 기록이다. 단순 변경 파일 목록이나 설계 문서의
복사본이 아니다.

### 생성 시점과 파일명

- 구현과 필수 검증을 마친 뒤, PR을 Ready for review로 전환하기 전에
  작성한다.
- Draft PR에서 확보한 PR 번호를 파일명과 본문에 사용한다.
- 파일명은 `YYYY-MM-DD-pr-<number>-<topic>.md` 형식을 사용한다.
- 모든 기능, 수정, 구조 변경 PR은 이력 문서를 포함한다.
- 이력 문서 자체의 오타 수정처럼 기록 가치가 없는 문서 전용 PR은
  새 이력 문서 생성을 생략할 수 있다.

예:

```text
docs/history/2026-10-01-pr-12-fsd-migration.md
```

### 필수 내용

- 날짜, PR 번호와 링크, 상태
- 관련 설계와 구현 계획 링크
- 작업 배경과 목표
- 작업 범위와 주요 변경
- 핵심 기술 결정과 선택 이유
- 사용자에게 보이는 변화
- 검증 명령과 실제 결과
- 제외 범위와 후속 작업

이력 문서에는 검증 결과를 새로 추측해 작성하지 않는다. 해당 PR에서
실제로 실행한 명령과 결과만 기록한다.

## 프로젝트 구조

Feature-Sliced Design을 현재 규모에 맞게 축소 적용한다.

```text
src/app/       Expo Router 라우트와 앱 초기화
src/pages/     화면 단위 슬라이스
src/widgets/   여러 기능을 조합한 큰 화면 블록
src/features/  사용자 행동 단위 기능
src/shared/    도메인에 독립적인 UI, 유틸리티, 설정
assets/        이미지와 폰트
```

- `src/app/`은 라우트와 `_layout.tsx`만 둔다.
- 실제 화면 구현은 `src/pages/<slice>/`에 둔다.
- 라우트 파일은 화면의 default export를 연결하는 얇은 진입점으로
  유지한다.
- 레이어는 `app → pages → widgets → features → shared` 방향으로만
  의존한다.
- 같은 레이어의 서로 다른 슬라이스는 직접 임포트하지 않는다.
- 슬라이스 외부에서는 `index.ts` public API를 사용한다.
- `shared`는 다른 FSD 레이어를 임포트하지 않는다.
- `entities`는 도메인 모델이 생기기 전까지 도입하지 않는다.
- 빈 `features`, `widgets`, `entities` 디렉터리를 미리 만들지 않는다.
- 파일명은 kebab-case, React 컴포넌트는 PascalCase, named export를
  기본으로 한다.
- 프로젝트 내부 임포트는 `@/` alias를 사용한다.

상세 이동 범위는 기존
`docs/superpowers/specs/2026-09-22-fsd-structure-design.md`를 기준으로
하며, 새 규칙 문서는 그 결정을 현재 구조 규칙으로 반영한다.

## 개발 규칙 범위

기존 `AGENTS.md`에서 다음 규칙은 유지하고 상세 문서로 정돈한다.

- Expo SDK 버전을 확인하고 해당 버전의 공식 문서를 우선한다.
- iOS와 Android만 지원하고 웹 전용 코드는 제거한다.
- Expo Router와 typed routes를 사용한다.
- CNG 프로젝트에서 `ios/`, `android/`를 직접 수정하지 않는다.
- iOS 전용 기능에는 Android 폴백을 제공한다.
- 새 의존성은 사전 승인 후 `npx expo install`로 추가한다.
- 상태는 지역 상태, Context, 외부 라이브러리 순서로 승급한다.
- 백엔드가 생기기 전에 API 레이어를 미리 만들지 않는다.
- NativeWind 도입 전에는 기존 테마 토큰과 `useTheme`을 사용한다.
- 비밀정보와 개인정보를 저장소나 로그에 남기지 않는다.
- 접근성, 모바일 성능, 다크 모드와 두 플랫폼 호환성을 확인한다.

## 검증 정책

검증은 변경 유형에 비례해 실행한다.

| 변경 유형 | 필수 검증 |
| --- | --- |
| TypeScript·React Native 코드 | `npx expo lint`, `npx tsc --noEmit`, 관련 테스트 |
| 의존성·Expo 설정 | 위 검증과 `npx expo-doctor` |
| UI·라우팅 | 코드 검증과 iOS·Android 수동 확인 |
| 네이티브 모듈 | 코드 검증과 개발 빌드 필요 여부 확인 |
| 문서만 변경 | `git diff --check`, 링크·경로·명령어 확인 |

- 실행하지 않은 검증은 통과했다고 기록하지 않는다.
- 기존 오류로 실패하면 요청 범위와의 관련성을 구분해 보고한다.
- 검증 명령이 자동 설치나 설정 변경을 요구하면 임의로 진행하지 않고
  의존성 추가 승인 규칙을 따른다.
- 코드 작업 완료 기준은 lint와 typecheck 통과다.
- 테스트 체계가 추가되면 관련 테스트 통과도 완료 기준에 포함한다.

## 배포와 보안

- EAS Build, Submit, Update는 각각 명시적 요청이 있을 때만 실행한다.
- 네이티브 런타임 변경은 OTA 업데이트로 배포하지 않는다.
- 환경별 빌드 프로필과 버전 정책은 실제 EAS 설정을 추가할 때
  `docs/rules/release.md`에 확정한다.
- `.env`, 토큰, 인증서와 비공개 API 키를 커밋하지 않는다.
- 공개 클라이언트 값과 비밀값을 구분하고 EAS Secrets 사용 기준을
  기록한다.
- OCR 이미지와 추출 데이터는 저장 기간, 접근 권한, 삭제 정책이
  승인되기 전까지 영구 보관하지 않는다.

## 구현 범위

규칙 체계 도입 작업은 다음 파일을 대상으로 한다.

- `AGENTS.md`를 핵심 제약과 상세 문서 링크 중심으로 재구성
- Expo 템플릿 상태인 `README.md`를 실제 프로젝트 안내로 교체
- `CONTRIBUTING.md` 생성
- `docs/README.md` 생성
- `docs/rules/architecture.md` 생성
- `docs/rules/development.md` 생성
- `docs/rules/workflow.md` 생성
- `docs/rules/documentation.md` 생성
- `docs/rules/release.md` 생성
- `docs/history/`용 PR 이력 템플릿 생성
- 기존 FSD 설계와 새 규칙 사이의 충돌 제거

실제 FSD 코드 이동은 프로젝트 규칙 문서 작성과 별도 PR로 실행한다.
규칙 문서는 목표 구조를 확정하지만, 문서 작업 PR에서 애플리케이션
코드를 함께 이동하지 않는다.

## 제외 범위

- FSD 디렉터리로 실제 코드 이동
- ESLint 설정과 레이어 제한 규칙 구현
- 테스트 프레임워크 도입
- NativeWind 도입
- GitHub 브랜치 보호 설정 변경
- PR 템플릿과 CI 워크플로 추가
- EAS 설정 파일과 빌드 프로필 생성

제외 항목은 규칙 문서에서 원칙을 정의할 수 있지만 외부 설정이나 새
의존성이 필요한 작업은 별도 승인과 별도 PR로 수행한다.

## 완료 기준

- 모든 규칙의 기준 문서가 한 곳으로 정해져 중복 설명이 없다.
- `AGENTS.md`와 승인된 FSD 설계의 구조 규칙이 충돌하지 않는다.
- commit, push, PR, 병합과 배포의 권한 경계가 구분된다.
- 명사형 커밋 제목과 본문 작성 규칙에 올바른 예시가 있다.
- Superpowers 설계·계획 문서 위치가 유지된다.
- PR별 이력 문서의 생성 시점, 파일명과 필수 항목이 정의된다.
- 변경 유형별 검증 명령과 실패 보고 방식이 정의된다.
- 새 참여자가 README와 문서 지도만으로 필요한 규칙을 찾을 수 있다.
